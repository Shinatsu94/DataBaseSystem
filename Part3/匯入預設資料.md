# 匯入預設資料

本文件說明 `範例資料.sql` 中每一段匯入程式碼的用途、執行順序與驗證意義。此檔案負責將教室租借系統需要的基礎資料、測試資料與可查詢資料匯入 MariaDB。

## 一、執行目的

`範例資料.sql` 的完整用途是建立一組可直接測試的教室租借系統資料。它包含十個實體各至少十筆資料，使 Part3 可以展示完整 Schema 是否能正確處理使用者、教室、節次、課程、長期借用、單次預約、審核與通知。

本檔案必須在 `完整資料庫Schema.sql` 執行完成後才能執行，因為它需要先有資料表、外鍵、檢查限制與觸發器。

## 二、匯入前設定

| 程式碼段落 | 用途 | 設計原因 |
| --- | --- | --- |
| `USE classroom_rental;` | 指定要匯入資料的資料庫 | 避免資料被寫入其他資料庫。 |
| `SET NAMES utf8mb4;` | 設定連線字元集 | 範例資料包含中文姓名、課程名稱、教室名稱與通知文字，必須支援 Unicode。 |
| `SET time_zone = '+08:00';` | 指定台灣時區 | 系統使用台灣校園情境，建立時間與審核時間應以 UTC+8 解讀。 |
| `START TRANSACTION;` | 開始交易 | 若匯入過程發生錯誤，可避免只匯入部分資料造成資料不一致。 |

完整用意：匯入前設定確保資料寫入正確資料庫、正確字元集與正確時間語意，並以交易保護整批匯入的完整性。

## 三、booking_statuses 狀態資料

此段使用 `INSERT INTO booking_statuses (...) VALUES ...` 匯入十種狀態。

| 匯入內容 | 用途 | 設計原因 |
| --- | --- | --- |
| `pending` | 表示申請已送出並等待審核 | 預約與長期借用的預設狀態。 |
| `approved` | 表示申請已核准 | 代表教室時段已正式被占用。 |
| `rejected` | 表示申請被拒絕 | 保留審核結果與拒絕紀錄。 |
| `canceled` | 表示申請已取消 | 使用者或管理端可保留取消紀錄。 |
| `draft` | 表示草稿 | 可用於尚未送出的申請資料。 |
| `under_review` | 表示審核中 | 用於需要多階段審核的情境。 |
| `expired` | 表示已逾期 | 避免過期申請仍被視為有效。 |
| `completed` | 表示借用已完成 | 可區分已結案資料。 |
| `suspended` | 表示暫停 | 可用於特殊情況暫停借用。 |
| `resubmission_required` | 表示需要補件或重新送出 | 支援退回修改流程。 |

執行順序原因：`booking_statuses` 必須先匯入，因為 `long_term_bookings`、`bookings` 與 `booking_reviews` 都會透過 `status_id` 外鍵參考此資料表。

完整用意：狀態資料建立整個系統的流程語意，使預約、長期借用與審核結果都能使用一致的狀態代碼。

## 四、users 使用者資料

此段使用 `INSERT INTO users (...) VALUES ...` 匯入學生、教師與管理員帳號。

| 匯入內容 | 用途 | 設計原因 |
| --- | --- | --- |
| 學生帳號 | 測試一般使用者送出預約、查看通知與查詢資料 | 對應學生身份權限。 |
| 教師帳號 | 測試課程授課者、長期借用與審核流程 | 對應教師身份權限。 |
| 管理員帳號 | 測試審核、維護與完整管理權限 | 對應管理員身份權限。 |
| 電子郵件 | 測試唯一限制 | 每一筆使用者資料必須具有不重複的 email。 |
| 系所或單位 | 提供查詢與報告顯示資料 | 可用於統計不同系所借用情形。 |

執行順序原因：`users` 必須在課程、長期借用、預約、審核與通知之前匯入，因為這些資料表都需要參考使用者。

完整用意：使用者資料建立系統身份基礎，使後續資料能驗證申請人、授課教師、審核者與通知接收者是否存在且身份正確。

## 五、classrooms 教室資料

此段使用 `INSERT INTO classrooms (...) VALUES ...` 匯入十間教室。

| 匯入內容 | 用途 | 設計原因 |
| --- | --- | --- |
| 教室代碼 | 作為教室主鍵 | 支援課程、長期借用與單次預約關聯。 |
| 教室名稱 | 顯示可讀名稱 | 方便報告、View 與使用者查詢。 |
| 容納人數 | 表示教室容量 | 支援依活動人數選擇教室。 |
| 啟用狀態 | 表示教室是否開放 | 可模擬維修、停用或不開放借用情境。 |

執行順序原因：`classrooms` 必須在 `course_times`、`long_term_bookings` 與 `bookings` 之前匯入，因為這些資料都會連接教室。

完整用意：教室資料建立可被借用的空間資源，使系統能驗證每筆課程與預約是否指向實際存在的教室。

## 六、sections 節次資料

此段使用 `INSERT INTO sections (...) VALUES ...` 匯入校園節次與時間。

| 匯入內容 | 用途 | 設計原因 |
| --- | --- | --- |
| 節次代碼 | 作為節次主鍵 | 課程與借用可使用固定節次表示。 |
| 節次名稱 | 提供畫面顯示 | 使用者可理解第幾節或午休時段。 |
| 開始時間 | 定義節次起點 | 支援時間區間判斷。 |
| 結束時間 | 定義節次終點 | 與開始時間共同形成完整節次。 |

執行順序原因：`sections` 必須在 `course_times`、`long_term_bookings` 與 `bookings` 之前匯入，因為這些資料表需要參考開始節次與結束節次。

完整用意：節次資料讓系統能使用學校既有作息表示教室借用時間，避免使用任意時間造成管理困難。

## 七、course_info 課程資料

此段使用 `INSERT INTO course_info (...) VALUES ...` 匯入十門課程。

| 匯入內容 | 用途 | 設計原因 |
| --- | --- | --- |
| 課程代碼 | 作為課程主鍵 | 支援課程時段關聯。 |
| 學年度 | 表示課程所屬年度 | 可區分不同學年度的同名課程。 |
| 學期 | 表示第一學期、第二學期或暑期 | 支援課程排程與查詢。 |
| 課程名稱 | 顯示課程名稱 | 用於 View 與查詢結果。 |
| 授課教師 | 指向 `users` | 觸發器會驗證授課者身份必須為教師或管理員。 |

執行順序原因：`course_info` 必須在 `users` 之後匯入，因為授課教師必須先存在於使用者資料表。

完整用意：課程資料建立校園固定使用教室的來源，使系統能把一般借用與課程排程放在同一個衝突檢查邏輯中。

## 八、course_times 課程時段資料

此段使用 `INSERT INTO course_times (...) VALUES ...` 匯入十筆課程固定時段。

| 匯入內容 | 用途 | 設計原因 |
| --- | --- | --- |
| 課程代碼 | 指向 `course_info` | 表示哪一門課使用此時段。 |
| 教室代碼 | 指向 `classrooms` | 表示課程使用哪間教室。 |
| 星期 | 表示固定上課日 | 使用 1 至 7 表示星期一至星期日。 |
| 開始節次 | 指向 `sections` | 表示課程開始時間。 |
| 結束節次 | 指向 `sections` | 表示課程結束時間。 |

執行順序原因：`course_times` 必須在 `course_info`、`classrooms` 與 `sections` 都匯入後才能執行。

完整用意：課程時段資料讓系統能判斷某間教室在特定星期與節次是否已被課程占用，進而防止借用申請與上課時間衝突。

## 九、long_term_bookings 長期借用資料

此段使用 `INSERT INTO long_term_bookings (...) VALUES ...` 匯入十筆長期借用。

| 匯入內容 | 用途 | 設計原因 |
| --- | --- | --- |
| 申請人 | 指向 `users` | 表示由誰提出長期借用。 |
| 教室 | 指向 `classrooms` | 表示借用哪一間教室。 |
| 開始日期與結束日期 | 定義借用期間 | 使用 `DATE` 表示年月日，不包含時分秒。 |
| 星期 | 表示每週固定借用日 | 適合社團、輔導或固定活動。 |
| 開始節次與結束節次 | 指向 `sections` | 表示每次借用的節次範圍。 |
| 借用原因 | 提供審核依據 | 使審核者理解借用目的。 |
| 狀態 | 指向 `booking_statuses` | 表示長期借用目前流程狀態。 |
| 建立時間 | 使用 `DATETIME(0)` | 表示申請建立的日期與時間。 |

執行順序原因：`long_term_bookings` 需依賴 `users`、`classrooms`、`sections` 與 `booking_statuses`，因此必須在這些基礎資料之後匯入。

完整用意：長期借用資料用於測試跨日期區間、固定星期與固定節次的借用情境，同時驗證觸發器能避免長期借用與課程時段發生衝突。

## 十、bookings 單次預約資料

此段使用 `INSERT INTO bookings (...) VALUES ...` 匯入十筆單次預約。

| 匯入內容 | 用途 | 設計原因 |
| --- | --- | --- |
| 申請人 | 指向 `users` | 表示提出預約的人。 |
| 教室 | 指向 `classrooms` | 表示預約使用的教室。 |
| 長期借用編號 | 可為 NULL | 若單次預約由長期借用展開，可追蹤來源。 |
| 課程時段編號 | 可為 NULL | 若預約與課程相關，可保留關聯。 |
| 預約日期 | 使用 `DATE` | 表示實際借用日期。 |
| 開始節次與結束節次 | 指向 `sections` | 表示借用時間範圍。 |
| 借用原因 | 提供審核依據 | 用於審核、查詢與報表。 |
| 狀態 | 指向 `booking_statuses` | 表示預約目前狀態。 |
| 建立時間 | 使用 `DATETIME(0)` | 保留申請時間。 |

執行順序原因：`bookings` 需依賴 `users`、`classrooms`、`sections`、`booking_statuses`，並可選擇性參考 `long_term_bookings` 與 `course_times`，因此必須在前述資料匯入後執行。

完整用意：單次預約資料用於測試教室租借系統的主要流程，包含送出預約、查詢預約、審核預約與檢查教室時段是否重疊。

## 十一、booking_reviews 審核紀錄資料

此段使用 `INSERT INTO booking_reviews (...) VALUES ...` 匯入十筆審核紀錄。

| 匯入內容 | 用途 | 設計原因 |
| --- | --- | --- |
| 預約編號 | 指向 `bookings` | 表示審核哪一筆預約。 |
| 審核者 | 指向 `users` | 觸發器會檢查審核者必須為教師或管理員。 |
| 審核狀態 | 指向 `booking_statuses` | 表示核准、退回、拒絕等結果。 |
| 審核意見 | 說明審核理由 | 提供申請者與管理者查看。 |
| 審核時間 | 使用 `DATETIME(0)` | 保留審核發生時間。 |

執行順序原因：`booking_reviews` 必須在 `bookings`、`users` 與 `booking_statuses` 之後匯入。

完整用意：審核紀錄資料用於驗證預約審核流程是否完整，並保留審核結果、審核人與審核時間。

## 十二、notifications 通知資料

此段使用 `INSERT INTO notifications (...) VALUES ...` 匯入十筆通知。

| 匯入內容 | 用途 | 設計原因 |
| --- | --- | --- |
| 接收者 | 指向 `users` | 表示通知要給誰。 |
| 預約編號 | 可為 NULL | 若通知與預約相關，可建立連結。 |
| 通知內容 | 顯示訊息 | 告知申請送出、審核結果或補件需求。 |
| 已讀狀態 | 使用 BOOLEAN | 支援未讀通知查詢。 |
| 建立時間 | 使用 `DATETIME(0)` | 依時間排序通知。 |

執行順序原因：`notifications` 必須在 `users` 之後匯入；若通知關聯預約，也必須在 `bookings` 之後匯入。

完整用意：通知資料讓系統能測試使用者接收審核結果、系統提醒與未讀通知查詢。

## 十四、資料筆數驗證查詢

此段使用多個 `SELECT COUNT(*)` 並透過 `UNION ALL` 合併結果。

| 查詢項目 | 用途 | 設計原因 |
| --- | --- | --- |
| `COUNT(*) FROM users` | 檢查使用者筆數 | 驗證使用者資料是否成功匯入。 |
| `COUNT(*) FROM classrooms` | 檢查教室筆數 | 驗證教室主檔是否完整。 |
| `COUNT(*) FROM sections` | 檢查節次筆數 | 驗證節次資料是否完整。 |
| `COUNT(*) FROM booking_statuses` | 檢查狀態筆數 | 驗證狀態主檔是否完整。 |
| `COUNT(*) FROM course_info` | 檢查課程筆數 | 驗證課程主檔是否完整。 |
| `COUNT(*) FROM course_times` | 檢查課程時段筆數 | 驗證課程排程是否完整。 |
| `COUNT(*) FROM long_term_bookings` | 檢查長期借用筆數 | 驗證長期借用資料是否完整。 |
| `COUNT(*) FROM bookings` | 檢查單次預約筆數 | 驗證預約資料是否完整。 |
| `COUNT(*) FROM booking_reviews` | 檢查審核紀錄筆數 | 驗證審核資料是否完整。 |
| `COUNT(*) FROM notifications` | 檢查通知筆數 | 驗證通知資料是否完整。 |

完整用意：筆數驗證查詢可快速確認十個實體是否都已成功匯入資料，並符合每一資料表至少十筆資料的要求。

## 十六、衝突測試註解

檔案最後保留兩段註解形式的 INSERT 測試。

| 測試內容 | 用途 | 設計原因 |
| --- | --- | --- |
| 測試課程時段衝突 | 驗證 `course_times` 觸發器 | 確認同一教室同星期同節次不能重複排課。 |

## 十七、完整總結

`範例資料.sql` 的整體作用是為教室租借系統建立一組完整、可驗證、可查詢的預設資料。它依照外鍵相依順序匯入狀態、使用者、教室、節次、課程、課程時段、長期借用、單次預約、審核紀錄與通知，並透過交易確保資料匯入一致。最後的筆數驗證、實務查詢與衝突測試註解，則用來確認資料庫 Schema、完整性限制與系統邏輯是否能正確運作。
