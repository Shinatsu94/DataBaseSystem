## 題目與應用情境

題目：**教室租用系統**

系統整合下列教室使用情境：

1. 學期固定課程安排教室與授課節次。
2. 學生申請專題討論、班會或校內活動空間。
3. 教師申請調課、補課、考試或週期性輔導教室。
4. 管理員審核申請並保存每次審核決策。
5. 系統檢查固定課表與已核准預約是否發生時段衝突。
6. 系統將審核結果寫入通知紀錄，供使用者查詢。

## 系統需求說明

### 功能性需求

功能性需求描述使用者實際需要完成的工作，以及系統應提供的回應。

#### 所有使用者

| 編號 | 使用者需要 | 系統應提供的功能 |
|---|---|---|
| FR-01 | 使用自己的身分進入系統 | 系統辨識登入者是學生、教師或管理員，並只顯示該身分可使用的功能與資料。 |
| FR-02 | 查看可借用的教室 | 使用者可依日期、節次、教室及容納人數查詢場地，並辨識教室是否啟用、是否已有固定課程或核准預約。 |
| FR-03 | 看懂學校的節次時間 | 系統顯示每一節的名稱、開始時刻與結束時刻，讓使用者不必自行換算時間。 |
| FR-04 | 查看自己的申請進度 | 使用者可查詢個人預約，並清楚看到草稿、待審核、審核中、已核准、已拒絕、待補件或已取消等狀態。 |
| FR-05 | 接收處理結果 | 系統在申請狀態改變時建立通知，內容應包含相關預約、處理結果及必要說明；使用者可標記通知為已讀。 |
| FR-06 | 查詢過去的借用紀錄 | 使用者可依日期與狀態查看自己的歷史申請、審核結果及通知，不得看到其他一般使用者的個人資料。 |

#### 學生

| 編號 | 學生需要 | 系統應提供的功能 |
|---|---|---|
| FR-07 | 申請一次性的教室使用 | 學生可選擇教室、日期、開始節次、結束節次並填寫用途，建立屬於自己的待審核預約。 |
| FR-08 | 在審核前修正資料 | 預約仍為待審核時，學生可修改教室、日期、節次或借用原因，也可取消自己的申請。 |
| FR-09 | 確認申請是否可送出 | 系統應檢查必填欄位、節次順序、教室啟用狀態及申請人身分，並以明確訊息說明無法送出的原因。 |

#### 教師

| 編號 | 教師需要 | 系統應提供的功能 |
|---|---|---|
| FR-10 | 使用學生可用的單次預約功能 | 教師可查詢教室、建立單次預約、追蹤狀態、查看審核結果及通知。 |
| FR-11 | 查看授課課程與固定課表 | 教師可查詢課程名稱、學年度、學期、授課教室、星期及節次安排。 |
| FR-12 | 申請固定週期的教室使用 | 教師可指定日期範圍、每週使用日、教室與節次，建立自己的週期性借用申請。 |
| FR-13 | 管理尚未審核的週期性申請 | 教師可修改或取消自己的待審核週期性借用，但不能修改其他教師的資料或自行核准案件。 |

#### 管理員

| 編號 | 管理員需要 | 系統應提供的功能 |
|---|---|---|
| FR-14 | 維護使用者、教室、節次與狀態 | 管理員可新增、查詢、修改及刪除基礎資料，並可停用暫時不能借用的教室。 |
| FR-15 | 維護課程與固定課表 | 管理員可建立課程、指定授課教師、安排教室與節次，並調整既有固定課表。 |
| FR-16 | 集中處理借用申請 | 管理員可查看全部單次與週期性申請，依申請內容進行核准、拒絕、取消、暫停或要求補件。 |
| FR-17 | 說明每一次審核決策 | 管理員處理案件時可填寫審核意見；系統須保存審核人、決策狀態及處理時間，不得覆寫先前歷程。 |
| FR-18 | 掌握教室使用情況 | 管理員可依教室、日期、申請人及狀態查詢使用紀錄，作為場地管理與後續報表依據。 |

#### 系統自動處理

| 編號 | 系統責任 | 系統應執行的功能 |
|---|---|---|
| FR-19 | 防止教室重複分配 | 核准預約或建立固定課表前，系統必須檢查相同教室、日期或星期及節次是否重疊。 |
| FR-20 | 保護資料所有權 | 學生與教師只能讀寫自己的申請與通知；只有管理員能查看及管理全部資料。 |
| FR-21 | 維持資料關聯正確 | 系統不得接受不存在的使用者、教室、節次、課程或狀態，也不得接受結束節次早於開始節次的資料。 |
| FR-22 | 保存完整處理紀錄 | 系統保存申請建立時間、審核時間、通知時間及目前狀態，使每筆案件都能追溯。 |

### 非功能性需求

非功能性需求定義系統功能必須達到的品質程度，以及用來保障品質的技術措施。尚未執行壓力測試或災難復原演練的數值，列為系統驗收目標。

| 編號 | 品質面向 | 品質與驗收目標 | 技術保障方式 |
|---|---|---|---|
| NFR-01 | 易用性 | 使用者應能在不理解資料庫欄位的情況下完成查詢與申請；表單應使用教室名稱、日期、節次及狀態中文名稱，錯誤訊息須說明原因與處理方式。 | 操作介面使用下拉選單、日期選擇器與必填提示；資料庫以 View 提供易於理解的資料範圍，應用程式將資料庫錯誤轉換為使用者可讀訊息。 |
| NFR-02 | 回應效能 | 一般教室查詢、個人預約與未讀通知，在 10 萬筆預約資料的驗收環境中，95% 請求應於 2 秒內回應；新增預約與衝突檢查應於 3 秒內完成。 | 使用複合索引支援教室日期、申請人日期、固定課表與未讀通知查詢；以 `EXPLAIN` 檢查執行計畫，並以測試資料進行基準測試。 |
| NFR-03 | 正確性 | 無效外鍵、重複唯一值、反向日期或節次、錯誤角色及重疊的已核准時段必須全部被拒絕，不得只依賴前端檢查。 | 使用 `PRIMARY KEY`、`FOREIGN KEY`、`UNIQUE`、`NOT NULL`、`DEFAULT`、`CHECK` 與 Trigger，在 MariaDB 層再次驗證。 |
| NFR-04 | 交易可靠性 | 一次操作涉及多筆資料時，必須全部成功或全部取消，不得留下只有預約而沒有審核或通知的部分資料。 | 所有資料表使用 `InnoDB`；應用程式以交易包覆相關 `INSERT`、`UPDATE`，發生錯誤時執行 `ROLLBACK`。 |
| NFR-05 | 存取安全 | 未授權使用者不得讀取或修改他人資料；學生與教師不得自行核准案件；正式密碼不得存放於專案或 SQL 檔案。 | 使用三種 MariaDB Role、`SQL SECURITY DEFINER` View、欄位級 `GRANT`、資料列條件與 Trigger；部署時使用強密碼、加密連線及安全的密碼管理方式。 |
| NFR-06 | 隱私保護 | 一般使用者只能看到本人帳號、預約、審核結果與通知；管理員存取個人資料應限於行政用途。 | 使用 `USER()` 將 MariaDB 登入帳號對應 `users.user_id`，由 View 隔離資料列；一般角色不授予基礎資料表查詢權。 |
| NFR-07 | 可追蹤性 | 每一次申請、審核與通知都必須能確認相關人員、狀態及事件時間；審核歷程不得被新的結果覆蓋。 | 使用獨立的 `booking_reviews` 歷程表；建立、審核與通知時間採 `TIMESTAMP(6)`，保留微秒級排序能力。 |
| NFR-08 | 可用性 | 在正常校園網路與資料庫服務可用時，使用者應可持續查詢及送出申請；單一不合法操作不得造成整個系統停止服務。 | 應用程式應處理資料庫例外並回復單次交易；資料庫連線使用逾時、重試與連線池設定，部署環境監控服務與連線狀態。 |
| NFR-09 | 備份與復原 | 正式環境至少每日備份一次；驗收目標為最多遺失 24 小時資料，並能在 4 小時內恢復資料庫服務。 | 使用 MariaDB 邏輯或實體備份、異地保存及定期還原演練；Schema 與初始化資料由 Git 版本控制保存。 |
| NFR-10 | 相容性與中文資料 | 系統必須正確保存繁體中文、英文、數字及常用符號；日期與時間不得因顯示環境不同而產生錯誤解讀。 | 資料庫使用 `utf8mb4` 與 `utf8mb4_unicode_ci`；鐘面時刻使用 `TIME(0)`、日曆日期使用 `DATE`、事件時間使用 `TIMESTAMP(6)`，連線明確設定時區。 |
| NFR-11 | 可維護性 | 資料庫結構、權限與 View 必須能由單一正式 Schema 重建；欄位名稱、限制名稱及文件應保持一致。 | 使用一份 `完整資料庫Schema.sql` 管理 DDL、Trigger、View 與 Role；每張資料表另有逐欄規格、型態理由及其他邏輯規則。 |
| NFR-12 | 可測試性 | 每次修改 Schema 後，必須能驗證物件數量、每表資料筆數、合法操作、越權操作及衝突案例。 | 提供 10 張資料表各至少 10 筆範例資料、查詢與 View 範例及驗證文件；測試須涵蓋接受案例與拒絕案例。 |
| NFR-13 | 擴充性 | 新增教室、課程、預約與通知時，不應修改既有交易資料結構；常用資料量增加後仍可透過索引與查詢調整維持效能。 | 採主資料與交易資料分離、第三正規化、代理鍵及外鍵設計；狀態集中於 `booking_statuses` 管理，避免在多張交易表重複定義。 |

## 身分與權限

| 身分 | MariaDB Role | 權限範圍 |
|---|---|---|
| 學生 | `classroom_student_role` | 查詢啟用教室、節次、狀態及自己的帳號、預約、審核結果與通知；建立、修改或取消自己的待審核單次預約；更新自己的通知讀取狀態。 |
| 教師 | `classroom_teacher_role` | 繼承學生權限；增加課程與固定課表查詢，以及自己的週期性借用建立、修改與取消權限。 |
| 管理員 | `classroom_admin_role` | 繼承教師權限；管理全部基礎資料、預約、週期性借用、審核紀錄、通知與 View。 |

學生與教師不能冒用其他帳號提出申請，也不能自行將案件改為核准狀態。資料列範圍由 View 控制，狀態與角色規則由 Trigger 再次驗證。

### 關聯說明

- 所有現有實體關聯均為 `1:N`。
- `bookings.long_term_id`、`bookings.course_time_id` 與 `notifications.booking_id` 可為 `NULL`，因此屬於選擇性參照。
- `bookings` 是核心交易實體；每一筆資料表示某一日實際發生或申請中的教室使用。
- `long_term_bookings` 保存週期性借用規則，不直接取代特定日期的 `bookings`。
- `booking_reviews` 採新增歷程方式保存決策，不覆寫既有審核紀錄。

### 完整性限制

| 類型 | 實作 | 目的 |
|---|---|---|
| 實體完整性 | `PRIMARY KEY` | 每筆資料具有不可重複且不可為空的識別值。 |
| 參照完整性 | `FOREIGN KEY` | 子資料只能參照已存在的父資料。 |
| 值域完整性 | `ENUM`、`CHECK`、無號整數 | 限制角色、狀態、星期、學期、容量、日期與節次範圍。 |
| 唯一性 | `UNIQUE` | 防止電子郵件、節次名稱及狀態代碼重複。 |
| 其他邏輯規則 | Trigger | 驗證教師、管理員、資料所有權、教室啟用狀態與時段衝突。 |
| 存取控制 | View、Role、欄位級 `GRANT` | 實作最小權限原則與個人資料隔離。 |

### 型態設計原則

- `CHAR(8)`：僅用於固定八碼的校內帳號。
- `VARCHAR(n)`：用於長度確實可變的名稱、電子郵件、教室代碼、課程代碼與狀態代碼。
- `TINYINT/SMALLINT UNSIGNED`：用於不允許負數且值域明確的小型數值。
- `BIGINT UNSIGNED AUTO_INCREMENT`：用於會長期累積的交易識別碼。
- `TEXT`：用於借用原因、審核意見及通知內容等不定長度敘述。
- `BOOLEAN`：用於教室啟用與通知已讀狀態。
- `TIME(0)`：保存每日鐘面時刻，精確至秒，不包含日期與時區。
- `DATE`：保存日曆日期，不包含時刻且不執行時區轉換。
- `TIMESTAMP(6)`：保存建立、審核及通知等事件時間，保留六位小數秒並依連線時區轉換。

## SQL：概念層到關聯式 Schema

概念層的「使用者提出預約」關聯，在 SQL 中轉換為 `bookings.applicant_id` 外鍵：

```sql
CREATE TABLE bookings (
  booking_id       BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  applicant_id     CHAR(8) NOT NULL,
  classroom_id     VARCHAR(10) NOT NULL,
  booking_date     DATE NOT NULL,
  start_section_id TINYINT UNSIGNED NOT NULL,
  end_section_id   TINYINT UNSIGNED NOT NULL,
  reason           TEXT NOT NULL,
  status_id        TINYINT UNSIGNED NOT NULL,
  created_at       TIMESTAMP(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  FOREIGN KEY (applicant_id) REFERENCES users(user_id),
  FOREIGN KEY (classroom_id) REFERENCES classrooms(classroom_id),
  FOREIGN KEY (status_id) REFERENCES booking_statuses(status_id),
  CHECK (start_section_id <= end_section_id)
) ENGINE=InnoDB;
```

概念層的「預約由管理員審核」關聯，在查詢中透過外鍵連接：

```sql
SELECT
  b.booking_id,
  applicant.username AS applicant_name,
  reviewer.username AS reviewer_name,
  status.status_name,
  br.reviewed_at
FROM booking_reviews AS br
JOIN bookings AS b ON b.booking_id = br.booking_id
JOIN users AS applicant ON applicant.user_id = b.applicant_id
JOIN users AS reviewer ON reviewer.user_id = br.reviewer_id
JOIN booking_statuses AS status ON status.status_id = br.status_id;
```
