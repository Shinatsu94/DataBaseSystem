## 專案題目與目標

專案題目：教室租用系統

本系統用於管理學校教室之固定排課與臨時借用。使用者得提出教室借用申請；管理員得審核案件；系統應保存審核歷程、傳送通知，並避免同一間教室在相同時段被重複使用。

系統處理的主要情境如下：

1. 學期開始前匯入表定課表。
2. 教師進行臨時調課。
3. 學生借用教室進行專題會議。
4. 班級借用教室召開班會或舉辦活動。
5. 課程另外借用考場。
6. 管理員查詢歷史紀錄與借用狀況。

## 資料庫設計方法

本專案依照關聯式資料庫設計流程進行：

1. 從使用案例辨識實體。
2. 辨識實體之間的關係與基數。
3. 將實體映射為資料表。
4. 為每張資料表指定主鍵。
5. 以外鍵表示 `1 : N` 關係。
6. 以 `NOT NULL`、`UNIQUE`、`CHECK` 與 Trigger 實作限制。
7. 以範例資料與錯誤案例驗證 Schema。

目前 Schema 共包含 10 張資料表：

| 分類 | 資料表 | 用途 |
|---|---|---|
| 主資料 | `users` | 保存學生、教師與管理員資料 |
| 主資料 | `classrooms` | 保存教室基本資料與啟用狀態 |
| 主資料 | `sections` | 保存學校節次與起訖時間 |
| 主資料 | `booking_statuses` | 保存預約審核狀態 |
| 課程資料 | `course_info` | 保存學期課程資訊 |
| 課程資料 | `course_times` | 保存固定課表安排 |
| 借用資料 | `long_term_bookings` | 保存長期借用計畫 |
| 借用資料 | `bookings` | 保存每一次實際借用 |
| 稽核資料 | `booking_reviews` | 保存管理員審核歷程 |
| 通知資料 | `notifications` | 保存申請狀態通知 |

### MariaDB 架構設定

| 設定 | 實作方式與目的 |
|---|---|
| 儲存引擎 | 所有資料表使用 `ENGINE=InnoDB`，由 MariaDB 執行外鍵檢查。 |
| 字元集 | 所有資料表使用 `DEFAULT CHARSET=utf8mb4`，支援繁體中文與 Unicode。 |
| 比對規則 | 所有資料表使用 `COLLATE=utf8mb4_unicode_ci`。 |
| 自動編號 | 交易資料表使用 MariaDB `AUTO_INCREMENT`。 |
| 時間欄位 | 節次起訖時間使用 MariaDB `TIME`。 |
| 衝突阻擋 | Trigger 使用 `SIGNAL SQLSTATE '45000'` 終止不合法異動。 |
| 星期轉換 | 使用 `WEEKDAY(date) + 1` 對應星期一至星期日之 `1` 至 `7`。 |

## 完整性限制分類

### 實體完整性

每一張資料表都必須有主鍵。主鍵用於唯一識別每一筆資料，不可為 `NULL`，也不可重複。

### 參照完整性

外鍵只能引用已存在的資料。例如 `bookings.classroom_id` 必須引用 `classrooms` 資料表中已存在的教室。正式 Schema 的所有資料表均使用 MariaDB `InnoDB` 儲存引擎，由資料庫執行外鍵參照完整性檢查。

### 域完整性

欄位必須符合允許的資料型態、格式或值域：

1. 使用者角色只能是 `student`、`teacher`、`admin`。
2. 預約狀態只能是 `pending`、`approved`、`rejected`、`canceled`。
3. 容納人數必須大於 `0`。
4. 星期必須介於 `1` 到 `7`。
5. 開始節次不可晚於結束節次。

### 商業規則

部分規則需要跨資料表查詢，無法只使用 `CHECK` 完成，因此以 Trigger 實作：

1. 同一間教室的固定課表不可重疊。
2. 已核准預約不可撞到固定課表。
3. 同一間教室、同一日期的已核准預約不可互相重疊。
4. 待審核案件得暫時並存；核准時必須再次執行衝突驗證。

## 各實體、欄位與完整性限制

每一個實體均具有獨立說明頁。獨立頁面包含用途、完整欄位表格、局部 Mermaid 實體關聯圖、每一項關聯之意義、使用範例與其他邏輯規則。

### 1. `users`：使用者

[開啟完整實體說明](./實體資料表格/01_users.md)

保存學生、教師與管理員的基本資料。課程授課教師、預約申請人、審核人與通知收件者皆引用此資料表。

| 欄位 | 型別 | 鍵值或限制 | 意義 |
|---|---|---|---|
| `user_id` | `CHAR(8)` | PK | 使用者唯一編號，不可為空且不可重複。 |
| `username` | `VARCHAR(30)` | `NOT NULL` | 使用者姓名。 |
| `email` | `VARCHAR(100)` | UK、`NOT NULL` | 電子郵件，可作為登入帳號與通知地址。 |
| `role` | `VARCHAR(10)` | `NOT NULL`、`CHECK` | 使用者身分，只允許 `student`、`teacher`、`admin`。 |
| `department` | `VARCHAR(50)` | 可為 `NULL` | 使用者所屬單位。 |

關聯：`users` 分別與 `course_info`、`long_term_bookings`、`bookings`、`booking_reviews`、`notifications` 形成 `1 : N` 關係。

### 2. `classrooms`：教室

[開啟完整實體說明](./實體資料表格/02_classrooms.md)

保存可被排課或借用的教室基本資料。

| 欄位 | 型別 | 鍵值或限制 | 意義 |
|---|---|---|---|
| `classroom_id` | `VARCHAR(10)` | PK | 教室唯一編號，例如 `A101`、`B205`。 |
| `classroom_name` | `VARCHAR(50)` | `NOT NULL` | 教室名稱。 |
| `capacity` | `INT` | `NOT NULL`、`CHECK (capacity > 0)` | 教室可容納人數。 |
| `is_active` | `TINYINT(1)` | `NOT NULL`、`DEFAULT 1`、`CHECK` | `1` 表示啟用，`0` 表示停用。 |

關聯：`classrooms` 分別與 `course_times`、`long_term_bookings`、`bookings` 形成 `1 : N` 關係。

### 3. `sections`：節次

[開啟完整實體說明](./實體資料表格/03_sections.md)

保存學校定義的上課節次與起訖時間，避免在不同資料表中重複輸入時間文字。

| 欄位 | 型別 | 鍵值或限制 | 意義 |
|---|---|---|---|
| `section_id` | `INT` | PK | 節次唯一編號。 |
| `section_name` | `VARCHAR(20)` | UK、`NOT NULL` | 節次顯示名稱，例如 `第 1 節`。 |
| `start_time` | `TIME` | `NOT NULL` | 開始時間，例如 `08:10:00`。 |
| `end_time` | `TIME` | `NOT NULL` | 結束時間，例如 `09:00:00`。 |

資料表層級限制：`CHECK (start_time < end_time)`。

關聯：`sections` 分別與 `course_times`、`long_term_bookings`、`bookings` 形成 `1 : N` 關係。

### 4. `booking_statuses`：審核狀態

[開啟完整實體說明](./實體資料表格/04_booking_statuses.md)

集中保存預約狀態，避免在不同交易資料表中重複輸入狀態文字。

| 欄位 | 型別 | 鍵值或限制 | 意義 |
|---|---|---|---|
| `status_id` | `INT` | PK | 狀態唯一編號。 |
| `status_code` | `VARCHAR(10)` | UK、`NOT NULL`、`CHECK` | 程式使用的狀態代碼。 |
| `status_name` | `VARCHAR(20)` | `NOT NULL` | 顯示給使用者看的狀態名稱。 |

`status_code` 允許值：

| 狀態代碼 | 中文意義 | 是否占用教室 |
|---|---|---|
| `pending` | 待審核 | 否 |
| `approved` | 已核准 | 是 |
| `rejected` | 已拒絕 | 否 |
| `canceled` | 已取消 | 否 |

關聯：`booking_statuses` 分別與 `long_term_bookings`、`bookings`、`booking_reviews` 形成 `1 : N` 關係。

### 5. `course_info`：課程資訊

[開啟完整實體說明](./實體資料表格/05_course_info.md)

保存學期課程資料，例如學年度、學期、課程名稱與授課教師。

| 欄位 | 型別 | 鍵值或限制 | 意義 |
|---|---|---|---|
| `course_id` | `VARCHAR(20)` | PK | 課程唯一編號。 |
| `academic_year` | `INT` | `NOT NULL` | 學年度，例如 `114`。 |
| `semester` | `INT` | `NOT NULL`、`CHECK` | 學期，只允許 `1` 或 `2`。 |
| `course_name` | `VARCHAR(100)` | `NOT NULL` | 課程名稱。 |
| `teacher_id` | `CHAR(8)` | FK、`NOT NULL` | 授課教師，參照 `users(user_id)`。 |

完整性規則：

1. 每門課都必須有授課教師。
2. 授課教師帳號必須已存在於 `users`。
3. Schema 目前以外鍵確保帳號存在；應用程式還應確認其 `role` 為 `teacher`。

關聯：`users` 與 `course_info` 形成 `1 : N`；`course_info` 與 `course_times` 形成 `1 : N`。

### 6. `course_times`：固定授課時間

[開啟完整實體說明](./實體資料表格/06_course_times.md)

保存課程固定排課資訊，包括課程、教室、星期與節次範圍。

| 欄位 | 型別 | 鍵值或限制 | 意義 |
|---|---|---|---|
| `course_time_id` | `INT` | PK、`AUTO_INCREMENT` | 固定排課紀錄編號。 |
| `course_id` | `VARCHAR(20)` | FK、`NOT NULL` | 對應課程，參照 `course_info(course_id)`。 |
| `classroom_id` | `VARCHAR(10)` | FK、`NOT NULL` | 授課教室，參照 `classrooms(classroom_id)`。 |
| `day_of_week` | `INT` | `NOT NULL`、`CHECK` | 星期，`1` 表示星期一，`7` 表示星期日。 |
| `start_section_id` | `INT` | FK、`NOT NULL` | 開始節次，參照 `sections(section_id)`。 |
| `end_section_id` | `INT` | FK、`NOT NULL` | 結束節次，參照 `sections(section_id)`。 |

資料表層級限制：`CHECK (start_section_id <= end_section_id)`。

Trigger 限制：

1. 新增固定課表時，同一間教室、同一星期不可與既有固定課表重疊。
2. 修改固定課表時，也必須再次進行相同檢查。
3. 新增或修改固定課表時，不可與已核准的單次預約重疊。

關聯：`course_info`、`classrooms`、`sections` 分別與 `course_times` 形成 `1 : N`；`course_times` 與 `bookings` 形成可選參照之 `1 : N`。

### 7. `long_term_bookings`：長期借用

[開啟完整實體說明](./實體資料表格/07_long_term_bookings.md)

保存週期性借用計畫的父單據。例如，一個專題小組在學期內每週二固定使用某間教室。

| 欄位 | 型別 | 鍵值或限制 | 意義 |
|---|---|---|---|
| `long_term_id` | `INT` | PK、`AUTO_INCREMENT` | 長期借用唯一編號。 |
| `applicant_id` | `CHAR(8)` | FK、`NOT NULL` | 申請人，參照 `users(user_id)`。 |
| `classroom_id` | `VARCHAR(10)` | FK、`NOT NULL` | 借用教室，參照 `classrooms(classroom_id)`。 |
| `start_date` | `DATE` | `NOT NULL` | 計畫開始日期。 |
| `end_date` | `DATE` | `NOT NULL` | 計畫結束日期。 |
| `day_of_week` | `INT` | `NOT NULL`、`CHECK` | 每週借用的星期。 |
| `start_section_id` | `INT` | FK、`NOT NULL` | 開始節次，參照 `sections(section_id)`。 |
| `end_section_id` | `INT` | FK、`NOT NULL` | 結束節次，參照 `sections(section_id)`。 |
| `reason` | `VARCHAR(200)` | `NOT NULL` | 長期借用原因。 |
| `status_id` | `INT` | FK、`NOT NULL` | 審核狀態，參照 `booking_statuses(status_id)`。 |
| `created_at` | `DATETIME` | `NOT NULL`、`DEFAULT CURRENT_TIMESTAMP` | 建立時間。 |

資料表層級限制：

1. `CHECK (start_date <= end_date)`
2. `CHECK (start_section_id <= end_section_id)`

設計說明：`long_term_bookings` 保存父單據；真正占用特定日期教室的紀錄仍由 `bookings` 保存。系統應透過程式將一筆長期借用展開為多筆 `bookings`。

關聯：`users`、`classrooms`、`sections`、`booking_statuses` 分別與 `long_term_bookings` 形成 `1 : N`；`long_term_bookings` 與 `bookings` 形成 `1 : N`。

### 8. `bookings`：單次預約

[開啟完整實體說明](./實體資料表格/08_bookings.md)

保存每一次實際發生的教室借用。此資料表是整個系統的營運核心。

| 欄位 | 型別 | 鍵值或限制 | 意義 |
|---|---|---|---|
| `booking_id` | `INT` | PK、`AUTO_INCREMENT` | 單次預約唯一編號。 |
| `applicant_id` | `CHAR(8)` | FK、`NOT NULL` | 申請人，參照 `users(user_id)`。 |
| `classroom_id` | `VARCHAR(10)` | FK、`NOT NULL` | 借用教室，參照 `classrooms(classroom_id)`。 |
| `long_term_id` | `INT` | FK、可為 `NULL` | 若由長期借用展開，保存父單據編號。 |
| `course_time_id` | `INT` | FK、可為 `NULL` | 若與固定課表相關，保存授課時間編號。 |
| `booking_date` | `DATE` | `NOT NULL` | 實際借用日期。 |
| `start_section_id` | `INT` | FK、`NOT NULL` | 開始節次，參照 `sections(section_id)`。 |
| `end_section_id` | `INT` | FK、`NOT NULL` | 結束節次，參照 `sections(section_id)`。 |
| `reason` | `VARCHAR(200)` | `NOT NULL` | 借用原因。 |
| `status_id` | `INT` | FK、`NOT NULL` | 目前審核狀態，參照 `booking_statuses(status_id)`。 |
| `created_at` | `DATETIME` | `NOT NULL`、`DEFAULT CURRENT_TIMESTAMP` | 申請建立時間。 |

資料表層級限制：`CHECK (start_section_id <= end_section_id)`。

Trigger 限制：

1. 當狀態為 `approved` 時，新增預約前必須檢查固定課表。
2. 當狀態為 `approved` 時，新增預約前必須檢查其他已核准預約。
3. 修改預約為 `approved` 時，必須再次執行相同檢查。
4. 待審核 `pending` 案件得暫時並存，不會立即占用教室。

完整性規則：

1. 借用教室與申請人必須存在。
2. 開始與結束節次必須存在。
3. 預約狀態必須存在。
4. 已核准預約不可和固定課表或其他已核准預約重疊。

關聯：`users`、`classrooms`、`sections`、`booking_statuses`、`long_term_bookings`、`course_times` 分別與 `bookings` 形成 `1 : N`；`bookings` 分別與 `booking_reviews`、`notifications` 形成 `1 : N`。

### 9. `booking_reviews`：審核歷程

[開啟完整實體說明](./實體資料表格/09_booking_reviews.md)

保存每一次審核動作。除了 `bookings` 中的目前狀態，系統也能追蹤歷史。

| 欄位 | 型別 | 鍵值或限制 | 意義 |
|---|---|---|---|
| `review_id` | `INT` | PK、`AUTO_INCREMENT` | 審核紀錄唯一編號。 |
| `booking_id` | `INT` | FK、`NOT NULL` | 被審核的預約，參照 `bookings(booking_id)`。 |
| `reviewer_id` | `CHAR(8)` | FK、`NOT NULL` | 執行審核的管理員，參照 `users(user_id)`。 |
| `status_id` | `INT` | FK、`NOT NULL` | 此次審核決定的狀態，參照 `booking_statuses(status_id)`。 |
| `comment` | `VARCHAR(300)` | 可為 `NULL` | 審核備註。 |
| `reviewed_at` | `DATETIME` | `NOT NULL`、`DEFAULT CURRENT_TIMESTAMP` | 審核時間。 |

完整性規則：

1. 審核紀錄必須屬於既有預約。
2. 審核人必須為既有使用者。
3. 審核狀態必須存在。
4. Schema 目前以外鍵確保 `reviewer_id` 存在；應用程式還應確認其 `role` 為 `admin`。

關聯：`bookings`、`users`、`booking_statuses` 分別與 `booking_reviews` 形成 `1 : N`。

### 10. `notifications`：通知

[開啟完整實體說明](./實體資料表格/10_notifications.md)

保存預約狀態通知與讀取狀態。

| 欄位 | 型別 | 鍵值或限制 | 意義 |
|---|---|---|---|
| `notification_id` | `INT` | PK、`AUTO_INCREMENT` | 通知唯一編號。 |
| `recipient_id` | `CHAR(8)` | FK、`NOT NULL` | 通知收件者，參照 `users(user_id)`。 |
| `booking_id` | `INT` | FK、可為 `NULL` | 相關預約；保留 `NULL` 可支援一般系統公告。 |
| `message` | `VARCHAR(300)` | `NOT NULL` | 通知內容。 |
| `is_read` | `TINYINT(1)` | `NOT NULL`、`DEFAULT 0`、`CHECK` | `0` 表示未讀，`1` 表示已讀。 |
| `created_at` | `DATETIME` | `NOT NULL`、`DEFAULT CURRENT_TIMESTAMP` | 通知建立時間。 |

關聯：`users` 與 `notifications` 形成 `1 : N`；`bookings` 與 `notifications` 形成可選參照之 `1 : N`。

## 實體關係總表

本系統現有資料關聯皆為 `1 : N`。局部圖使用實線表示必填外鍵，虛線表示子實體之外鍵允許為空值。

| 父實體 | 子實體 | 基數 | 外鍵 | 意義 |
|---|---|---|---|---|
| `users` | `course_info` | `1 : N` | `course_info.teacher_id` | 一位教師得教授多門課程。 |
| `course_info` | `course_times` | `1 : N` | `course_times.course_id` | 一門課程得具有多個授課時段。 |
| `classrooms` | `course_times` | `1 : N` | `course_times.classroom_id` | 一間教室得安排多筆固定課表。 |
| `users` | `bookings` | `1 : N` | `bookings.applicant_id` | 一位使用者得提出多筆借用。 |
| `classrooms` | `bookings` | `1 : N` | `bookings.classroom_id` | 一間教室得累積多筆不同時間之借用紀錄。 |
| `long_term_bookings` | `bookings` | `1 : N` | `bookings.long_term_id` | 一筆長期借用得展開為多筆實際日期預約。 |
| `course_times` | `bookings` | `1 : N` | `bookings.course_time_id` | 課程相關借用得選擇參照固定授課時間。 |
| `bookings` | `booking_reviews` | `1 : N` | `booking_reviews.booking_id` | 一筆借用得具有多筆審核歷程。 |
| `bookings` | `notifications` | `1 : N` | `notifications.booking_id` | 一筆借用得產生多筆通知。 |
| `booking_statuses` | `bookings` | `1 : N` | `bookings.status_id` | 每筆預約都有一個目前狀態。 |
| `sections` | `course_times`、`long_term_bookings`、`bookings` | `1 : N` | 各資料表的 `start_section_id`、`end_section_id` | 所有借用與排課共用相同節次定義。 |

可選參照：

| 子實體欄位 | 父實體 | 意義 |
|---|---|---|
| `bookings.long_term_id` | `long_term_bookings` | 一般單次預約無須參照長期借用父單據。 |
| `bookings.course_time_id` | `course_times` | 非課程相關借用無須參照固定授課時間。 |
| `notifications.booking_id` | `bookings` | 一般系統通知無須參照單次預約。 |

## 防止衝突的 Trigger

| Trigger | 觸發時機 | 檢查內容 |
|---|---|---|
| `trg_course_times_prevent_overlap_insert` | 新增固定課表之前 | 檢查同一教室、同一星期是否已有節次重疊的固定課表或已核准預約。 |
| `trg_course_times_prevent_overlap_update` | 修改固定課表之前 | 執行與新增固定課表相同的檢查，並排除正在被修改的原始紀錄。 |
| `trg_bookings_prevent_overlap_insert` | 新增 `approved` 預約之前 | 檢查指定日期、教室與節次是否撞到固定課表或其他已核准預約。 |
| `trg_bookings_prevent_overlap_update` | 修改 `approved` 預約之前 | 執行與新增預約相同的檢查，並排除正在被修改的原始預約。此規則包含將 `pending` 案件改為 `approved` 的情況。 |

節次重疊判斷條件：

```sql
NEW.start_section_id <= existing.end_section_id
AND NEW.end_section_id >= existing.start_section_id
```

## 執行方式

進入本目錄後，依序執行：

```powershell
mariadb -u root -p -e "CREATE DATABASE IF NOT EXISTS classroom_rental CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
mariadb -u root -p classroom_rental < schema.sql
mariadb -u root -p classroom_rental < examples.sql
```

使用其他 MariaDB 管理工具時，應先建立 `classroom_rental` 資料庫，再依序執行：

1. [`schema.sql`](./schema.sql)
2. [`examples.sql`](./examples.sql)

正式 Schema 的所有資料表均明確指定 `ENGINE=InnoDB`，並使用 `DEFAULT CHARSET=utf8mb4` 與 `COLLATE=utf8mb4_unicode_ci`。
