# 組員心得

班級：四資工三甲

這次專題我們在製作「教室租用系統」的資料庫設計，對我來說是一個把資料庫課程觀念完整串起來的練習。剛開始看到題目時，我原本以為教室租借只是單純記錄誰在什麼時間借了哪一間教室，但真正開始分析後才發現，實際情境比想像中複雜很多。系統不只要處理學生或教師的申請，還要考慮固定課表、長期借用、單次預約、審核流程、通知紀錄，以及不同身分之間的權限差異。

在設計過程中，我印象最深的是 ER Diagram 與資料表之間的轉換。從一開始整理使用者、教室、節次、課程、預約、審核、通知等實體，到後來把它們轉成 MariaDB 中的十張資料表，每一步都需要仔細思考關聯是否合理。例如 users 與 bookings 是一對多關係，classrooms 也會被多筆預約或課程時段使用；而 booking_reviews 則負責保留每一次審核紀錄，讓系統不只是記錄最後結果，也能追蹤處理過程。這讓我更理解資料庫設計不是只把資料存起來，而是要讓資料能支援真實的業務流程。

這份專案也讓我更熟悉完整性限制的重要性。以前在寫 SQL 時，常常只注意欄位型態和主鍵，但這次我們加入了 Primary Key、Foreign Key、Unique、Check Constraint，以及 Trigger 來限制不合理的資料。例如不能讓不存在的使用者提出申請、不能讓非教師帳號被指定為授課教師、不能讓停用教室接受已核准預約，也不能讓同一間教室在相同日期與節次重複借用。這些限制讓我體會到，資料庫本身也可以承擔一部分規則檢查，而不是全部交給前端或後端程式處理。

另外，View 與 Role 的設計也讓我學到權限控管的概念。學生、教師和管理員看到的資料範圍不同，如果直接開放基礎資料表，會有資料外洩或誤修改的風險。

因此透過 View 包裝查詢結果，再搭配 MariaDB Role 與 GRANT 設定不同身分的操作權限，可以讓系統更接近實際應用的安全需求。這部分讓我覺得資料庫設計不只是技術題，也和系統管理、使用者隱私及資料安全有關。

在完成專案的過程中，我也感受到團隊合作與文件整理的重要性。這次內容包含需求分析、ER 圖、資料表規格、完整 Schema、範例資料、View 查詢、驗證說明和簡報，如果沒有清楚的檔案分類與說明，後面要檢查或修改會非常困難。透過這次分工，我學到不只是把 SQL 寫出來而已，還要能說明每個欄位、限制與關聯的設計理由，讓其他人可以理解這個資料庫為什麼這樣設計。

整體來說，這次專題讓我對資料庫設計有更完整的認識。從概念層的需求分析，到邏輯層的資料表規劃，再到實體層的 SQL Schema、Trigger、View 與權限驗證，我更清楚一個系統背後需要哪些資料結構支撐。雖然過程中需要反覆修改欄位、關聯和限制條件，但也因為這些調整，讓我更能理解資料庫設計必須兼顧正確性、可維護性和實際使用情境。未來如果還有機會延伸這個專案，我希望能進一步加入前端介面與後端 API，讓目前完成的資料庫設計真正變成一套可以操作的教室租借系統。
